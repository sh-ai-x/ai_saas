Cost-optimized portfolio operating profile

The default profile optimizes for a credible portfolio and near-zero fixed monthly infrastructure cost. It deliberately keeps the first release as a modular monolith with extraction-ready contracts:

DatabaseOne Neon PostgreSQL project, one primary branch, DrizzleConnection, storage, availability, or tenant-isolation threshold
Durable workInngest Hobby for bounded workflows; local Docker for developmentExecution quota, concurrency, runtime, or data-residency pressure
EdgeCloudflare DNS/SSL/basic protection; Turnstile where neededAdvanced WAF, high traffic, or edge compute requirement
AI runtimeProvider abstraction and bounded calls inside the initial app/workflowLong execution, tool isolation, GPU/runtime needs, or queue depth
PaymentsMock by default; one live provider per environment, Toss or Lemon SqueezyRegional rollout, recurring billing, tax, or reconciliation volume
ObservabilityStructured logs, sampled OTel, provider-native basic tracesIncident volume, retention, evaluation scale, or compliance
CI/CDGitHub Actions plus Vercel Git deploymentMulti-service images, migrations, rollback, or AWS extraction
AWS workerOff by default; optional ECS Fargate Spot RunTask, 0.25 vCPU/0.5 GB ARM, public subnet, no ALB/NAT, no inbound rulesLong execution, worker isolation, or queue pressure with an approved variable-cost ceiling

The free profile must fail closed at quotas, never create hidden paid resources, and expose usage counters. The portfolio demo should use synthetic/mock payment records and low-cost model settings by default. LLM inference, payment processing fees, custom domains, and commercial provider plans are variable costs and are not treated as guaranteed free.

AWS Low-Cost Worker Mode is intentionally a worker-only profile. The public web/API remains on Vercel Hobby or Cloudflare Workers Free, and the worker has no inbound route. AWS documents public-subnet Fargate with an assigned public IP as a supported outbound pattern; this avoids a NAT Gateway, but the security group must deny inbound traffic. Fargate Spot is allowed only because LangGraph checkpoints and idempotent retries make interruption recoverable. ALB, private-subnet NAT, multi-AZ replicas, and always-on worker services are outside the low-cost profile.

Official plan references used for this cost profile: Vercel Hobby (https://vercel.com/docs/plans/hobby), Inngest Hobby (https://www.inngest.com/pricing), and Cloudflare Workers Free limits (https://developers.cloudflare.com/workers/platform/pricing/). Neon plan eligibility and limits must be checked in the account before each deployment rather than hard-coded into the application contract.

Initial baseline and target migration

mysaas is the initial version of this foundation, not a competing architecture. Preserve its first vertical slice: Next.js 16.3 App Router, Better Auth, Drizzle, Neon-compatible PostgreSQL, Vercel for the web surface, Inngest for initial background work, and Docker Compose for local development.

Portfolio Mode accepts one deployable modular monolith because its acceptance target is contract-level MSA alignment. AWS Low-Cost Worker Mode promotes only the agent-worker into an on-demand Fargate Spot task; the web/gateway remains on the free-tier host. Identity, project, billing, and admin remain owned modules on the shared data path. This is the smallest physical split that creates meaningful worker isolation without paying for a nine-service topology.

The migration sequence is: (1) formalize identity, tenant, billing, and run contracts around the existing app; (2) add transactional provider-neutral billing and the admin audit boundary; (3) ship the portfolio demo on the free profile; (4) introduce queue-backed run state and SSE replay; (5) extract FastAPI/LangGraph workers only after a budget and workload gate; and (6) retain Vercel/Neon for the web and primary data path unless a later ADR changes that decision.

Scope and acceptance contract

Build a deployable, cost-controlled foundation for enterprise AI services. The portfolio release must cover multi-tenant identity, Google OAuth, admin operations, bounded LangGraph runs, SSE replay, atomic metering, provider-neutral billing, mock payments, sampled OTel, CI/CD, and a reproducible local environment. Toss or Lemon Squeezy is enabled as one live provider per environment after the mock path passes; both adapters remain contract-tested.

A payment success page never grants access. Only a verified provider event or an explicitly audited admin action can change entitlement or credits. Mock actions are test-only and must be visibly separated from live records.

Google authentication and admin page

Google login uses a server-side authorization-code flow. The callback validates state, issuer, code, exact redirect URI, and provider subject before creating or linking the local account. Provider secrets, codes, and sensitive identity payloads never enter browser bundles, agent context, logs, or traces.

The admin page calls server-side admin-operations APIs. Each mutation resolves the operator, checks role and resource scope, validates the target, captures before state, requires a reason, applies a shared use case, and records actor/action/target/before/after/correlation/time in an append-only audit event. MVP may use super-admin, but the boundary remains replaceable by RBAC and must gain step-up/MFA before production.

Toss, Lemon Squeezy, and mock payment

Billing uses the Ports-and-Adapters pattern with application-owned capability ports and a provider registry. Toss Payments and Lemon Squeezy are separate adapters. The domain depends only on shared ports and normalized events; it never imports provider SDKs or provider status strings. The common flow is pending internal order → provider proof or query → durable inbox → dedupe → normalized event → transactional entitlement/ledger/audit.

Toss requires server-side order and amount comparison, persisted idempotency keys, payment query recovery, provider-specific webhook proof, and application-owned billing-key scheduling where recurring billing is enabled. Lemon Squeezy requires raw-body X-Signature verification, event allowlisting, exact store/product/variant mapping, subscription-state normalization, and replay/reconciliation.

The mock adapter is enabled only in non-production environments. Its admin controls create deterministic success, failure, duplicate, delayed, out-of-order, cancellation, refund, and unknown-state events. It uses the same provider ports, inbox, dedupe, entitlement, credit ledger, and audit path as real providers and never writes plan or credit state directly.

Dependency-ordered phases

  1. Cost-controlled vertical slice: preserve mysaas, add contracts, Google login, admin audit, mock billing, metering, and Docker/Vercel deployment.
  2. Durable lifecycle: add bounded runs, Inngest-backed retries, checkpoints, SSE replay, pending orders, and provider inbox.
  3. Verification: deterministic CI, RLS isolation, OAuth replay, admin denial/audit, provider replay, ledger concurrency, and E2E evaluator.
  4. Portfolio hardening: sampled OTel, redaction, usage counters, quota pause behavior, and documented free-tier operational limits.
  5. Conditional extraction: only if the budget/workload gate passes, add FastAPI/LangGraph worker, ECS/Fargate, Terraform, and multi-service deployment.

Each phase must have a runnable verification artifact before it can be marked complete.

Non-goals and open decisions

Non-goals are domain-specific agent workflows, always-on AWS resources in the portfolio profile, universal physical database-per-service deployment, and real payment processing in local development.

Open decisions are the service-extraction threshold from the initial mysaas slice, Inngest versus Redis/Celery/SQS for long-running agent work, whether Better Auth remains the extracted identity implementation, whether Toss and Lemon launch together, staging availability of mock payment controls, admin MFA/step-up policy, and repository/database extraction thresholds. Neon + Drizzle + Better Auth + Vercel are the initial baseline decisions, not unresolved prerequisites for the first increment. The cost gate must approve any new always-on resource and record its monthly ceiling, free-tier assumption, and removal plan.

After (proposed state)

A cost-tiered foundation removes the ambiguity between portfolio cost and worker isolation. Free Portfolio Mode uses the mysaas slice as one deployable modular monolith with logical MSA contracts. AWS Low-Cost Worker Mode adds only an on-demand ECS Fargate Spot agent-worker, while keeping the web/API on a free-tier host and the data on one Neon PostgreSQL cluster. This preserves low fixed cost without provisioning ALB, NAT, or a nine- service topology. Google OAuth is server-side, admin mutations are audited, Toss and Lemon Squeezy are Ports-and-Adapters, and mock payment follows the same ledger path in non-production.

Pros

  • Uses a working initial vertical slice instead of requiring a full rewrite before the first deployable increment.
  • Minimizes fixed cost by running one deployable app, one database, and one durable workflow path before service extraction.
  • Makes the trade-off explicit: Free Portfolio Mode optimizes cost, while AWS Low-Cost Worker Mode adds only interruptible worker isolation.
  • Produces a credible portfolio artifact with Google auth, admin operations, payment lifecycle, metering, and AI workflow evidence without requiring an always-on AWS stack.
  • Separates domain invariants from provider-specific payment APIs through capability ports and adapters.
  • Makes Google login, admin actions, payment events, mock scenarios, and AI runs observable and auditable.
  • Keeps the extraction path open through versioned contracts and deterministic replay/concurrency evidence.

Cons

  • Fargate Spot workers can be interrupted and public-subnet networking has a larger exposure surface; mitigate with checkpoint/retry, no inbound worker rules, and Cloudflare/Vercel as the only public web boundary.
  • Toss and Lemon Squeezy differ in payment semantics; mitigate with a Ports-and-Adapters pattern: provider-specific adapters implement shared capability ports and normalized events, while only one live provider is enabled per environment.

Limitations

  • Free Portfolio Mode is for personal/demo and low-volume validation; AWS Low-Cost Worker Mode adds variable usage cost but does not provide commercial SLA or multi-AZ high availability.
  • Real payment launch still requires provider sandbox/live verification; mock payment is evidence of application flow, not provider certification.
