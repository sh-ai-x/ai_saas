Multi-region and DR

Scenario 4 adds multi-region to the foundation API:

  • Primary region (ap-northeast-2, Seoul): ECS service (2 tasks), Aurora writer, S3 bucket.
  • Secondary region (ap-northeast-1, Tokyo): ECS service (1 task, warm standby), Aurora cross-region replica (async, lag ≤ 5s under normal load), S3 cross-region replication.
  • Route 53 failover record on api.<domain>: ALB health check triggers DNS failover ≤ 60s.
  • RPO / RTO: RPO ≤ 5 min (Aurora replication lag), RTO ≤ 2 min (Route 53 failover + ECS warm task in Tokyo).

The LangGraph checkpoint store is single-region primary; cross-region copy is async. Failover loses the in-flight checkpoint (the run is marked failed and can be resumed from the last persisted state).

For scenarios 1–3, single-region is the default. Multi-region is a deliberate spend; do not enable until product-market fit.

Security and IAM boundaries

The agent's existing rules R7 / R12 carry over without modification.

  • IAM task execution role has bedrock:InvokeModel, secretsmanager:GetSecretValue on the prefix ai-saas/<env>/*, s3:PutObject on the artifact bucket, logs:CreateLogStream on the foundation log group. Nothing else. sagemaker:* is not granted in the cost-minimal baseline.
  • Bedrock invocation logs are written to a dedicated CloudWatch log group with 30-day retention. Tenant ID is redacted before write (the kernel redaction.py already does this).
  • Secrets live in Secrets Manager under ai-saas/<env>/<key>; ECS tasks pull them at startup; never embedded in the image.
  • WAF rules on the ALB: rate-limit 100 req/min on /v1/runs, block known bad ASNs, AWS managed ruleset AWSManagedRulesCommonRuleSet.
  • VPC: foundation + sandbox tasks run in private subnets; ALB in public subnets; NAT gateway for outbound only when Bedrock requires it.
  • Tenant isolation is enforced at the application layer (existing auth.py checks x-tenant-id). No shared DB row crosses tenants.

Migration path (phased)

The proposal ships as four phases, each independently shippable.

Phase 1 (already done) — Local Lite + offline slice. PR #33. agent_platform/, project_packs/, services/, infra/profiles/local-lite/.

Phase 2 (in progress) — Vercel + Fly.io + multi-model. Branch docs/proposal-deployment-spec. LLM_PROVIDER env wiring, OpenAI-compatible adapter, docker:stage, benchmark harness.

Phase 3 (next, ~2 weeks) — AWS managed services. Add infra/aws/terraform/ (VPC, RDS, S3, ECS, ALB, IAM, Secrets Manager). Wire Fly.io foundation to point at RDS / S3 / Bedrock. Enable Bedrock in stage; A/B test against Groq for cost.

Phase 4 (later, only when traffic justifies) — Multi-region AWS. Route 53 failover, Aurora cross-region replica, Tokyo warm standby. No SageMaker in any phase. If a model Bedrock lacks becomes required, the cost-minimal path is Ollama on a rented GPU box (~$0.30/hr spot), not SageMaker. Full scenario 4 cost model validated against actual production traffic before committing.

Each phase is gated by the same release gates (recall, precision, latency, tokens, zero-tolerance checks). No phase is "done" without a green benchmark run + green prod-traffic canary.

What stays the same

Rules R1–R14 (rules/proposal-to-verified-change-agent.md) and the existing ports in agent_platform/ports.py are not modified. The StructuredModelPort Protocol already covers Ollama / vLLM / Bedrock / SageMaker / Together / Groq / OpenAI via the same JSON Schema request shape. The SandboxPort contract is unchanged; Fargate replaces the Local Lite subprocess only at the boundary. The DeliveryPort gains a GitHub adapter but keeps the same sign(**kwargs) / validate(request) shape. No upstream consumer of the kernel is affected.

Open questions for review

  1. Aurora vs Neon for prod? Aurora gives full AWS integration but ~$60/mo idle floor. Neon Launch stays free until 0.5 GB. Decide based on whether RDS failover and cross-region replica are must-haves. Default stays on Neon for the cost-minimal baseline.
  2. No SageMaker in any phase. If a model Bedrock lacks becomes required, the cost-minimal path is Ollama on a rented GPU box (~$0.30/hr spot, RunPod / Vast.ai / Lambda Labs), shut down when idle. That decision lives in a separate proposal.
  3. Cost anomaly alerts — CloudWatch anomaly detection on Bedrock InputTokenCount per tenant; alert at 2× weekly average. Open: what is the right Slack channel?
  4. On-call rotation — even on the cost-minimal path, two platforms (Vercel + Fly.io) means the on-call needs runbooks for both. See docs/runbooks/ which this proposal creates.

Before / After

Before (current state)

The current deployment story is single-platform: docker:local for dev, docker:stage for staging with Neon, and a planned Vercel production deploy that excludes the foundation API (which has no Vercel-native home for the long-running Python + SQLite + LangChain stack). There is no AWS footprint yet, no managed inference, no cross-region DR, and no concrete cost model per scenario. Model selection for the LLM adapter is ad-hoc; production picks are made by hand against unverified benchmarks. The agent's DeliveryPort only has a deterministic placeholder — no signed PR/CI adapter exists.

After (proposed state)

A cost-minimal deployment matrix scoped to what a single AI engineer can actually run and demo. The baseline is Vercel (web) + Fly.io (foundation Docker) + Neon (Postgres) + Bedrock (managed LLM, pay-per- token), no GPU self-hosting, no multi-region. AWS appears only as the optional prod-promotion target once product-market fit justifies the spend. The agent gets a real LLM adapter (OpenAI Chat Completions API), a multi-model benchmark harness, and a signed Git/CI delivery adapter. AWS heavy services (ECS Fargate, Aurora Serverless v2, Cloud Front, multi-region, SageMaker) are listed explicitly as deferred to a separate cost-justified proposal — they ship only when traffic or compliance demands them, not on day one.

Files

  • infra/aws/terraform/main.tf

    Root module: VPC (multi-AZ), ECR repos for foundation + sandbox + web, ECS Fargate cluster, RDS Aurora Serverless v2 (Postgres), S3 bucket for artifacts, IAM roles for task execution + Bedrock + SageMaker.

  • infra/aws/terraform/ecs.tf

    ECS Fargate services: foundation (1+ tasks), sandbox-worker (1+ tasks, larger CPU/RAM), inference (optional, see §3). ALB in front; WAF rules for /v1/*.

  • infra/aws/terraform/rds.tf

    Aurora Serverless v2 cluster, single writer + 1 reader in stage, 1 writer + 2 readers in prod. Encrypted at rest with KMS, backups retained 14 days (stage) / 35 days (prod). Drizzle uses the cluster endpoint (DATABASE_URL_UNPOOLED).

  • infra/aws/terraform/s3.tf

    ai-saas-artifacts-<env> bucket, versioning on, lifecycle rules push review artifacts to Glacier after 90 days. SSE-KMS. Public access blocked; presigned URLs only.

  • infra/aws/terraform/route53_cf.tf

    Route53 hosted zone, ACM certificate, CloudFront distribution with two origins (Vercel for the web, ALB for foundation). Failover routing policy on /api/foundation/*; latency on the rest.

  • infra/aws/terraform/bedrock.tf

    Bedrock model access for Claude Sonnet, Haiku, Llama 3.1 70B. Cross-region inference profile for resilience. SageMaker is NOT in scope for the cost-minimal baseline; if a model not in Bedrock becomes required, that goes to a separate proposal.

  • services/agent_orchestrator/remote_model.py

    OpenAICompatibleStructuredModel adapter (Ollama, vLLM, Bedrock via proxy, SageMaker via proxy, Together, Groq, Fireworks, OpenRouter). Strict JSON Schema response_format, retry with idempotency key.

  • services/delivery_gateway/github_adapter.py

    Real DeliveryPort adapter: creates a signed branch + draft PR via PyGithub or REST, dispatches a policy-gated GitHub Actions workflow via repository_dispatch, scoped token per tenant.

  • scripts/run-benchmark.py

    Multi-model benchmark harness: runs the proposal→plan→verify pipeline against N configured models, scores requirement_recall / evidence_precision / unsupported_claim_rate / p95 latency / tokens, writes results/<model>.json.

  • scripts/llm-serve.sh

    Launcher for Ollama / vLLM / llama.cpp / Bedrock proxy based on env LLM_RUNNER; pulls from HuggingFace if needed.

  • infra/models/models.yaml

    Model registry: tiny / default / quality / remote tiers with HF repo, runner, quantization, json_schema capability, RAM/VRAM.

  • benchmarks/cases/

    Fixed regression set (10–20 cases) for the benchmark harness: toss-subscription-sandbox, faq-support-decision, proposal-decompose, evidence-grounding, prompt-injection-defense, large-repo-context.

  • docs/runbooks/aws-prod.md

    Operator runbook: deploy order, rollback, on-call queries (RDS failover, ECS task restart, Bedrock throttling response).

Pros

  • Matches each workload to its native platform: Vercel CDN for the web, Fly.io for low-ops Docker, AWS for managed Postgres + heavy compute + global failover.
  • Production LLM picks are evidence-backed: benchmark harness scores each candidate against a fixed regression set; default in models.yaml is the cheapest model that clears all gates.
  • AWS footprint is IaC-only (Terraform); no manual console drift. Same code path for stage and prod via Terraform variables.
  • Cost ceiling per scenario is enumerable from the Terraform plan output; cost surprises show up at review time, not at month-end.
  • Sandbox worker moves to ECS Fargate with allowlisted task definitions; same contract as the Local Lite DeterministicSandbox but with real subprocess isolation.
  • Multi-region failover for the foundation API (active/active via Route53 + ALB); RPO ≤ 5 min via Aurora cross-region replication for prod.
  • DeliveryPort gains a real GitHub adapter with scoped tokens; signed PR + repository_dispatch workflow = auditable hand-off without ambient deploy credentials.
  • Bedrock gives managed Claude / Llama without managing GPUs. SageMaker self-hosting is intentionally excluded from the cost-minimal baseline — pay-per-token Bedrock beats self-hosting until traffic justifies a dedicated endpoint, and that decision lives in a separate proposal when traffic arrives.

Cons

  • Three platforms to operate (Vercel + Fly.io + AWS). On-call must know all three. Mitigated by Terraform owning AWS and runbooks for Fly/Vercel.
  • Aurora Serverless v2 ACU minimum is 0.5; idle cost ~$40/month even when zero traffic. Mitigated by stopping stage outside business hours.
  • Bedrock pay-per-token can spike if a runaway run burns the budget. Mitigated by the existing TokenBudgetLedger failing closed at plan-only 20k / verify 41k tokens; cost ceiling per run is hard-coded into the kernel, not a soft alert.
  • Bedrock quotas vary by region; us-east-1 has the broadest catalog but is the slowest for KR users. Mitigated by cross-region inference profile + CloudFront latency routing.
  • Terraform state in S3 + DynamoDB adds one more piece to bootstrap. Mitigated by infra/aws/terraform/bootstrap.sh one-shot script.
  • ECS Fargate cold start (10–30s) shows up on the verify path. Mitigated by min_capacity=1 in prod, autoscale on CPU.

Limitations

  • No Kubernetes, no ECS Fargate, no SageMaker, no Aurora, no multi-region in the baseline. The cost-minimal path is Vercel + Fly.io + Neon + Bedrock only. AWS service expansion (ECS, Aurora, multi-region) requires a separate cost-justified proposal.
  • Bedrock does not (yet) expose Qwen models. If a Qwen-only workflow is needed, that goes to a separate proposal with its own cost ceiling (likely Ollama on a rented GPU box, not SageMaker).
  • Multi-region active/active is for read-mostly endpoints. The LangGraph checkpoint store is single-region primary with async cross-region copy; failover loses the in-flight checkpoint but does not lose history.
  • No SOC2 / HIPAA / PCI controls in scope. The proposal ships the IaC for VPC + KMS + IAM boundaries, but the compliance audit itself is a separate track.
  • Sandbox worker on Fargate inherits the same allowlist semantics as the Local Lite DeterministicSandbox; production-grade untrusted-code isolation (gVisor / Firecracker microVM) is a separate proposal.
