Branch protection rules

`main` is protected in GitHub:

  • Require pull request reviews: ✅ 1 approval (configurable per repo)
  • Require status checks: ✅ /dev-kit:maintenance, /dev-kit:review (3-dim), foundation-ci
  • Require linear history: ✅ (squash merge preferred)
  • Require up-to-date branches: ✅
  • Include administrators: ✅
  • Allow force push: ❌
  • Allow deletion: ❌

*`release/` is semi-protected**: same status checks, but force-merge (no squash) allowed for cherry-picks.

One PR = one merged commit on main = one production deploy.

Vercel deployment config

vercel.json (repo root) drives web deploys:

{
  "git": {
    "deploymentEnabled": {
      "main": true,
      "feat/*": true,
      "fix/*": true,
      "release/*": true,
      "docs/*": false,
      "chore/*": false,
      "plan/*": false,
      "design/*": false
    }
  },
  "github": { "silent": false, "autoAlias": true },
  "buildCommand": "pnpm --filter ai-saas-foundation-web build",
  "outputDirectory": "apps/web/.next",
  "framework": "nextjs",
  "regions": ["icn1"]
}

Behavior:

  • Every push to feat/* / fix/* creates a preview URL.
  • Push to release/* deploys to a named staging alias (stage.<domain>).
  • Merge to main deploys to the production alias (<domain>).
  • PR comment posts the preview URL.

Fly.io foundation deploy

.github/workflows/fly-deploy.yml (NEW):

on:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      app:
        description: 'Fly app name'
        required: true
        default: 'ai-saas-foundation-stage'
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: superfly/flyctl-actions/setup-flyctl@master
      - run: flyctl deploy --strategy bluegreen --wait-timeout 300
  • Merge to main → Fly deploys ai-saas-foundation (prod) via bluegreen.
  • Manual workflow_dispatch → deploys to stage.

PR preview slot allocation

  • Each PR gets a Fly app ai-saas-foundation-pr-<n> (n = PR number).
  • Created by a bot on PR open; deleted on PR close.
  • DB: each preview app points at a Neon preview branch (Neon branching API), auto-deleted with the app.

The Fly bluegreen strategy means rollback is always to the previous release, never to "no release". Vercel keeps every deployment for 90 days; rollback is instant.

Before / After

Before (current state)

Branch and deploy conventions are scattered across worktree names, ad-hoc GitHub Actions, and individual operator memory. There is no documented mapping from branch class to environment; the worktree-guard hook enforces "no main edits" but does not specify what each new branch SHOULD be named. Hotfixes have no documented fast-path. Rollback procedures exist as tribal knowledge (Vercel CLI flags, flyctl flags) but are not in the repo. AWS Phase 3 has no branch-to-env mapping yet.

Evidence

  • .worktrees/ — 50+ active worktrees with mixed prefix conventions (feat/, fix/, plan/, design/, docs/, chore/, refactor/, test/)
  • No vercel.json deploymentEnabled rule; every PR triggers a preview regardless of branch type
  • .github/workflows/fly-deploy.yml missing — Fly foundation deploys via manual flyctl deploy today
  • No branch protection documented; PRs merge without recorded approvals in some cases
  • No release/* branch precedent; version bumps go straight main → tag via /dev-kit:ship

After (proposed state)

A typed branch vocabulary, explicit branch-protection rules, a PR lifecycle tied to Vercel + Fly + Neon previews, hotfix + rollback paths per surface, and an extension path for AWS Phase 3 that requires no rule changes. The worktree-guard hook remains as the hard block; this proposal is the soft guidance that complements it.

Files

  • vercel.json

    Add git.deploymentEnabled per-branch map; auto-deploy for main / feat/ / fix/ / release*; skip docs / plan / design / chore that only touch docs or non-app paths.

  • .github/workflows/fly-deploy.yml

    New workflow: flyctl deploy --strategy bluegreen on push to main, plus workflow_dispatch for manual stage deploys.

  • .github/workflows/branch-cleanup.yml

    Weekly janitor: delete remote branches whose PR is merged or closed, prune local refs, post a summary comment.

  • docs/runbooks/hotfix.md

    Operator runbook: hotfix branch off main, fast-track review, Vercel auto + Fly bluegreen + post-mortem PR template.

  • docs/runbooks/rollback.md

    Per-surface rollback recipes (Vercel / Fly / Neon / LangSmith datasets / secrets) with copy-pasteable commands.

  • .github/workflows/ci.yml

    Add a "Validate stage compose override merges cleanly" step that runs docker compose -f docker/prod/compose.yaml -f docker/stage/compose.yaml --env-file /dev/null config -q. Ships in this PR.

Pros

  • Branch class is a single tag (feat/, fix/, release/, hotfix/) — no one has to guess what a branch is for.
  • Auto-deploys from feat/* give every PR a free preview without explicit bot action.
  • Hotfix path is one branch + one PR + one review + merge; no special tooling.
  • Vercel rollback is a single CLI call (vercel rollback); Fly rollback is a single CLI call (fly releases rollback). Both keep N previous releases for instant restore.
  • AWS Phase 3 fits the same matrix with one extra column — no rule changes needed.
  • PR preview slot math (per-PR Fly app + Neon preview branch) prevents the "40 worktrees on port 3100" collision from leaking into prod.
  • Branch cleanup is automated weekly; no orphaned refs accumulate.

Cons

  • Per-PR Fly preview apps cost real money (~$5/mo each if kept warm). Mitigated by auto-destroy on PR close; only open PRs incur cost.
  • Vercel preview URLs leak app code paths to anyone with the URL. Mitigated by vercel.json password protection on preview deployments if a leak is detected.
  • Branch protection rules can be bypassed by repo admins. Mitigated by Include administrators: true and PR body check.
  • Linear history requirement blocks some cherry-pick workflows. Mitigated by release/* being semi-protected with force-merge allowed.
  • The branch taxonomy is opinionated; new contributors may pick the wrong prefix. Mitigated by a CLAUDE.md snippet and the worktree-guard hint message.

Limitations

  • No monorepo-aware deploys yet. If a single PR touches apps/web/, services/, and infra/, Vercel + Fly both deploy independently; there is no coordination gate. AWS Phase 3 will need a deploy-coordinator.yml if cross-service atomicity becomes important.
  • No canary deploys to a percentage of users. Vercel supports it on Pro plan; Fly supports it natively via bluegreen weights. Both are out of scope until Phase 4 (prod-full).
  • No DB-migration-gated deploys. A PR that adds a migration and a code rollback can leave the schema ahead of the code. Mitigated by Neon branching (preview DB per PR) and the convention "expand-migrate-then-contract" but not enforced by automation.
  • Branch cleanup is weekly; long-running PRs may stick around for 7 days. Acceptable; urgent cleanup is a manual git push origin --delete.
