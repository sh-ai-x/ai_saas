Decision

브라우저 폴더 전체를 코드 레포 snapshot으로 만드는 현재 흐름을 기본 경로에서 내리고, Markdown-first local document workspace를 기본 제품으로 채택한다.

사용자의 폴더 선택 경험은 유지한다. 차이는 선택 직후 모든 파일을 업로드하지 않고, 문서 manifest를 먼저 계산한다는 점이다. 기본 허용 대상은 .md, .mdx, .markdown, README*, CHANGELOG*, CONTRIBUTING*이며 .git, .worktrees, node_modules, 빌드 산출물, .env*, 바이너리와 첨부파일은 제외한다.

Pivot rationale and decision record

이 pivot은 선호가 아니라 현재 실행 결과와 제품 제약을 근거로 결정한다.

따라서 결정 기준은 무료 로컬 실행, 현재 UI 재사용, 25MiB 실패의 사전 차단, 코드 실행/패치 책임을 범위에서 제거다. 이 기록은 이후 코드 분석을 다시 기본 범위로 넣을 때 필요한 근거와 비용 증가를 비교할 기준선으로 유지한다.

User flow

  1. 사용자가 3019의 Workspace에서 디렉터리를 선택한다.
  2. 브라우저가 문서 파일만 순회하고 파일 수·총 용량·제외 목록을 계산한다.
  3. 사용자가 N개 문서 / M MB 업로드를 확인한다.
  4. 문서 snapshot만 Foundation에 업로드한다.
  5. UI는 문서 구조, 링크, 근거, 제안서 상태를 보여준다.
  6. 코드 분석/실행 버튼은 기본 화면에 노출하지 않는다.

Cost policy

기본 경로는 기존 Docker local stack과 SQLite/Postgres 저장소만 사용한다. LLM 호출은 사용자가 제안서 생성이나 문서 질의를 명시적으로 실행할 때만 bounded call로 수행한다. 전체 디렉터리를 매번 embedding하거나 지속적인 agent loop를 실행하지 않는다.

초기 문서 import는 현재 안전 한도를 유지하되, 요청 전체 multipart 오버헤드와 문서 내용량을 별도로 계산해 사용자에게 사전 안내한다. 한도를 무작정 늘리지 않고, 큰 문서는 문서 선택/제외 후 다시 가져오게 한다.

Acceptance criteria

  • mywiki처럼 코드와 작업트리가 함께 있는 폴더에서 .worktrees와 코드 파일이 업로드되지 않는다.
  • 업로드 전 UI에 문서 파일 수와 총 바이트가 표시된다.
  • 25MiB 정책을 넘는 경우 Foundation까지 요청하지 않고 명확한 안내가 나온다.
  • 작은 Markdown 레포는 기존 Docker local 환경에서 import → read authorization → proposal 생성까지 동작한다.
  • UI와 API 어디에서도 이 기능을 코드 실행/패치 적용 기능으로 설명하지 않는다.
  • 기존 repository snapshot API와 tenant read scope 계약은 문서 snapshot에서도 유지된다.

Non-goals

이 제안은 로컬 파일을 수정하거나, GitHub에 push하거나, 소스 코드를 자동 실행하거나, 무료 사용자를 위해 별도 외부 인프라를 추가하는 계획이 아니다. 코드 분석이 필요한 팀은 향후 별도 opt-in pack으로 분리한다.

Before / After

Before (current state)

현재 로컬 레포지토리 선택은 브라우저가 선택한 디렉터리의 파일을 모두 수집해 multipart 요청으로 Foundation snapshot에 업로드한 뒤, Git snapshot을 만든다. .git·node_modules 등 일부 디렉터리는 제외하지만 Markdown, 첨부파일, .worktrees와 기타 코드 파일을 구분하지 않아 문서 분석에 필요하지 않은 데이터까지 전송한다.

Evidence

  • apps/web/components/repository-workspace/repository-selector.tsx:75-83 — 현재 제외 목록에는 .git/node_modules/.next/dist/build/coverage/__pycache__만 있고 Markdown·코드·.worktrees 구분이 없다.
  • apps/web/components/repository-workspace/repository-selector.tsx:184-207 — 선택 디렉터리의 모든 통과 파일을 File 객체로 수집해 multipart 업로드한다.
  • foundation/server.py:36,633-639 — import 요청 전체 Content-Length를 25MiB로 제한한다.
  • services/control_api/repository_catalog.py:365-376 — snapshot 파일 총량도 25MiB로 제한한다.
  • Docker log — mywiki import는 POST /v1/repositories/import 400(repository import is empty or too large), 작은 README multipart는 같은 프록시에서 201 Created였다.
  • apps/web/app/api/foundation/[...path]/route.ts:31-57 — Next 프록시가 브라우저 multipart 본문을 Foundation으로 전달한다.

After (proposed state)

제품의 기본 단위를 코드 레포 분석기가 아니라 Markdown 중심의 로컬 문서 워크스페이스로 정의한다. 폴더 선택은 유지하되 업로드 전에 문서 파일만 필터링하고 파일 수·총 용량·제외 항목을 사용자에게 보여준다. Foundation에는 .md/.mdx/.markdown과 README/CHANGELOG/ CONTRIBUTING 계열 문서만 snapshot으로 저장하고, 제안서 생성 시 해당 문서의 근거와 문서 간 링크 구조를 분석한다. 코드 실행, 컴파일, 테스트, 패치 생성은 이 제품 범위에서 수행하지 않는다.

  • apps/web/components/repository-workspace/document-manifest.ts

Pros

  • [3/3] 비용과 전송량을 직접 줄인다 — 현재 selector가 통과시키는 모든 파일을 업로드한다(apps/web/components/repository-workspace/repository-selector.tsx:184-207). Markdown allowlist와 .worktrees 제외로 LLM 입력·Docker 저장소·네트워크 사용량을 문서량으로 제한한다.
  • [3/3] 현재 실패 원인을 제품 정책으로 해소한다 — mywiki import가 25MiB 요청 경계에서 400을 반환했지만 작은 README import는 201이었다(Docker log). 문서 전용 사전 계산으로 400까지 업로드한 뒤 실패하는 흐름을 없앤다.
  • [3/3] 구현 복잡도가 낮다 — 기존 브라우저 폴더 선택, Foundation multipart route, snapshot 저장, tenant read scope를 재사용하고 파일 분류와 manifest 계약만 좁힌다.
  • [3/3] 보안·프라이버시 경계를 명확히 한다 — .env, .git, .worktrees, 코드와 바이너리를 기본 전송하지 않아 자격 증명·내부 작업트리·불필요한 원문 노출을 줄인다(apps/web/components/repository-workspace/repository-selector.tsx:75-83).
  • [2/3] UI 가치가 선명해진다 — 사용자는 코드 분석 결과가 아니라 문서 목록, 문서 간 링크, 근거 문장, 문서 기반 제안서 상태를 확인한다. 현재 UI가 ‘Choose a repository directory’와 ‘repository’ 중심으로 표현된 상태에서 문서 워크스페이스로 제품 언어를 정렬할 수 있다.
  • [2/3] 무료 로컬 실행 모델과 맞는다 — 기존 Docker local profile의 Foundation/Postgres를 그대로 사용하고 별도 클라우드 인덱서·백그라운드 worker·유료 벡터 DB를 요구하지 않는다.
  • [2/3] 확장 경로가 남는다 — 이후 코드 분석이 필요할 때도 동일한 문서 manifest 계약에 선택적 source-code pack을 추가할 수 있어 기본 사용자의 비용을 증가시키지 않는다.

Cons

  • [1/3] 코드 변경·컴파일·테스트 검증을 제공하지 않는다 — 제품 문구와 UI에서 문서 분석 전용임을 명시하고, 코드 검증은 별도 개발 도구/후속 pack의 책임으로 제한한다.
  • [1/3] Markdown 외 문서 형식은 기본 제외된다 — PDF/이미지/노션 export 등은 텍스트 추출 pack이 필요할 때만 별도 opt-in으로 추가한다.
  • [1/3] 문서만으로 제안의 사실성이 부족할 수 있다 — Git commit/branch 같은 비콘텐츠 메타데이터와 문서 경로를 근거에 포함하되, 소스 코드 사실을 주장하는 제안은 생성하지 않도록 출력 계약에서 제한한다.

Limitations

  • 코드의 실제 동작·런타임·테스트 통과 여부는 이 워크스페이스의 보장 범위가 아니다. 향후 별도 code-analysis pack으로 확장한다.
  • 대용량 첨부파일과 PDF/OCR 분석은 범위 밖이다. 향후 문서 추출 pipeline을 별도 비용/용량 정책으로 추가한다.
  • 실시간 원본 폴더 동기화는 하지 않는다. 사용자가 다시 폴더를 선택해 문서 snapshot을 갱신하는 pull 모델을 사용한다.
  • 문서 근거의 의미적 정확성은 모델 품질에 의존한다. deterministic manifest/link 검증과 LangSmith trace로 실행 근거를 남기되, 문서 내용 자체의 진실성을 자동 보증하지 않는다.
